## (1) CRITICAL — costing traffic or indicating a penalty right now

### 1.1 Google is actively crawling old Joomla URLs today, and most of them 404
This is not a theoretical risk — it's happening. A 10-hour slice of today's access log (`/var/www/vhosts/fishbucklake.com/logs/access_ssl_log`, log only goes back to 03:44 today because Plesk log rotation reset it) already shows Googlebot requesting:

- `/index.php/lodges1/33-gallery/lodges-gallery`
- `/index.php/gallery-2/26-gallery`
- `/index.php/cabins/white-owl-lake-outpost`
- `/index.php/lodges1/21-trip-planner/31-packing-list`
- `/index.php/gallery-2?id=38`
- `/?option=com_content&view=article&id=3&Itemid=115`
- `/?option=com_content&view=article&id=19&catid=17&Itemid=214`

Some of these are caught by an existing (undocumented) set of 17 Rank Math redirect rules and 301 correctly. The `?option=com_content&view=article&id=X` style ones are **not** — WordPress just serves the homepage for any unrecognized query string, so Google gets a silent **200 on the homepage** instead of a 301 to the real replacement page. That's a soft-404: it tells Google "this old URL is now the homepage," which dilutes homepage relevance and wastes crawl budget instead of transferring the old page's authority to its actual replacement.

Beyond what's in today's log, I reconstructed a larger representative sample of ~28 old Joomla content/menu URLs from the surviving Joomla database (see §2.1 for method) and tested them against production:

| Result | Count (of 28 sampled) |
|---|---|
| 200 (resolves, usually via an existing redirect) | 3 |
| 301 → 404 (redirects to a clean WP-style path that doesn't exist) | 24 |
| 200 coincidentally (homepage regardless of query string) | 1 |

**Why it matters:** every 404'd old URL that had accumulated PageRank/backlinks/ranking history from up to 3+ years of Joomla operation loses that equity permanently once Google recrawls and drops it. This is the single biggest lever in this audit.

**Fix:** Build a complete redirect map from the old Joomla DB (I've extracted the raw data — see §2.1) to the current WP URLs, and add it to Rank Math's Redirections module (already active, already partially used — see below). Do **not** implement without your review, as instructed.

**Effort:** Medium — the data extraction is done; mapping ~45 published articles + ~10 menu paths to their WP equivalents and entering them is a few hours of careful work, ideally cross-checked against Google Search Console's "Pages" report (see §1.1 access note below) rather than my reconstruction alone.

**What I could not determine / access needed:** I do not have Google Search Console access for this property. GSC's Coverage/Pages report would show the *actual* set of old URLs Google has indexed or attempted to crawl (ground truth), rather than my reconstruction from Joomla's routing rules, which is a best-effort approximation of what the old SEF URLs *would have looked like*, not a captured record of what was actually crawled. The live access log only covers ~10 hours (see below on log retention) — not enough to see the full pattern. I'd recommend pulling the GSC "Pages — Not indexed" and "Excluded" lists before finalizing the redirect map.

### 1.2 Someone already built a partial redirect map — it doesn't match the real old URL structure
Rank Math's Redirections module is active and already has **17 manually-created rules** (table `fbl_rank_math_redirections`), evidently added ad hoc during/after migration. Examples: `index.php/faq` → `/faqs/`, `index.php/contactus` → `/contact-us/`, `index.php/27-location` → `/location/`.

These were clearly typed from memory/guesswork rather than derived from the actual Joomla SEF routing (`sef=1`, `sef_rewrite=0` — see §2.1), because they don't match the URL patterns Joomla actually generated (e.g., the real location article URL was `index.php/location/12-location`, not `index.php/27-location`). Some happen to still catch real Googlebot traffic (see §1.1), which is good luck rather than design. Whoever did this had the right idea but incomplete data.

**Fix:** Supersede with the complete map from §2.1, verified against Joomla's actual `#__content` / `#__menu` data.
**Effort:** Low once §1.1's map is approved — it's the same Rank Math UI already in use.

### 1.3 Live production database still contains the entire compromised Joomla schema
`FBL_LIVE` (the current live WordPress database) contains **~140 `lqyfi_`-prefixed Joomla tables** — the full Joomla 3/4 schema (content, users, sessions, Akeeba backup tooling, BreezingForms, JomRes, etc.) — sitting alongside the WordPress tables. This appears to have happened during the DB migration (whole database imported/merged rather than just the WP tables extracted).

**Why it matters:** not a direct SEO issue, but it's compromise residue in a production database: old Joomla user/session/credential tables persisting in a DB that's actively queried by the live site, unnecessary bloat, and a housekeeping red flag given the JCE compromise history. Not itself exploitable (nothing loads these tables anymore), but worth cleaning up as part of closing out the incident.
**Fix:** Export and archive `lqyfi_*` tables elsewhere, then drop them from `FBL_LIVE`. Requires a write to prod DB — outside this audit's scope, flagging for your sign-off.
**Effort:** Low (mechanical), but should be done by whoever owns the migration, with a backup first.

### 1.4 A live webshell sits in the quarantined Joomla tree
`httpdocs_QUARANTINED_2026-06-22/wp-nonce380.php` is a heavily obfuscated (goto-chain, hex-escaped strings) PHP file dated 17 June 2026 — the day of the JCE compromise. This is almost certainly the attacker's backdoor. I confirmed the quarantined directory is **not web-accessible** (`/httpdocs_QUARANTINED_2026-06-22/...` returns 404 on both production and staging1 hostnames), so it poses no live risk as-is. Also present in the same tree: `phpinfo.php` (info disclosure) and `index_r.html` (a "Site Under Maintenance" defacement page), consistent with a compromised-and-quarantined site.
**Why it matters:** not an SEO issue directly, but it's the actual evidence of how the compromise happened and what was left behind, and it's sitting on disk unencrypted with normal file permissions readable by the hosting account.
**Fix:** Not an SEO fix — flagging for your security follow-up. Recommend archiving the quarantined tree off-server (for any forensic/insurance need) and then deleting it from the VPS, once you're satisfied nothing else needs to be recovered from it.
**Effort:** Low.

### 1.5 71 published "pages" — roughly a third are unrelated theme demo content, live and indexed
The active theme is a Divi child theme, but the site is also running a large amount of leftover **Divi/booking-theme demo content** as real, published, indexed WordPress pages: `Shop`, `Cart`, `Checkout`, `Login`, `Account Login`, `Transaction Failed`, `Booking Canceled`, `Typography`, `Slider and Carousel`, `WordPress Blocks`, `Rooms – List/Grid/Compact/Background View`, `SoonToCome`, `aatest`, `Gallery - General images` (slug `gallery-testing`), `404 Page` (published as a normal page, not the actual 404 handler).

All of these are in the **live Rank Math sitemap** (`page-sitemap.xml`) that's currently submitted to Google, meaning Google is being told to index a WooCommerce cart/checkout flow and demo typography pages for a fly-in fishing lodge that doesn't sell products through this site.

**Why it matters:** this is exactly the kind of low-value/irrelevant content that drags down a whole site's perceived quality in Google's eyes (thin-content and site-quality signals are site-wide, not just per-page), and it wastes crawl budget that should go to the ~35 pages that are actual content. Given this site has "never had SEO attention" and just went through a security incident, cleaning this up is high-leverage and low-risk.
**Fix:** Set these to `draft` or `noindex` (or delete if truly unused) and remove from the sitemap. This is a content/publish-status change, not code — flagging for your review before I touch anything.
**Effort:** Low–Medium (needs a human decision per page on keep/kill, but the mechanics are trivial).

### 1.6 Every page shares the same H1 text — real page content never gets an H1
Every page on the site renders **5–6 `<h1>` tags**, and on the pages I sampled (home, outposts, hunting, FAQs, shop, catch-gallery) they're the *same* three: "FLY-IN", "Fishing and Hunting", "HORNEPAYNE" — these come from a global Divi hero/slider module included in the site header, not from page-specific content. On top of that, individual page builder content also uses `<h1>` styling for things like "Summer" / "Winter" / "Get In Touch" on the Contact page — so H1 is being used as a generic "big heading" style throughout Divi, not as the semantic page title.

**Why it matters:** no page on the site has a unique, content-describing H1. Google still uses H1 as a strong topical signal, and right now every page's H1 profile is identical, sitewide boilerplate — none of it says "Buffalo Island Lake Outpost" or "Fly-In Moose & Bear Hunts" on those respective pages.
**Fix:** This is a theme/template fix: change the hero/slider module to not use `<h1>`, and set each page's actual title (already unique per-page in Rank Math's SEO title field, so the raw material exists) as the one true H1. Given the token-driven CSS architecture already in place, this is a Divi module-settings change (module → advanced → heading level), not a rebuild.
**Effort:** Medium — needs care since a global header module changing tag level affects every page at once; worth testing on staging1 first.

## (2) STRUCTURAL — redirects, canonicals, sitemap, indexability

### 2.1 URL continuity — full detail and the extracted old-URL data
**Was Joomla using SEF URLs?** Yes: `configuration.php` shows `$sef = '1'`, `$sef_rewrite = '0'`, `$sef_suffix = '0'`. That means Joomla's search-engine-friendly router was on, but **without** `mod_rewrite` — so URLs kept `index.php` in them, e.g. `https://fishbucklake.com/index.php/information/49-rates` rather than a clean `/rates`. This matters because it changes exactly what string old URLs contain, which is why the current ad-hoc redirects (§1.2) mismatch.

**Old data recovered (read-only, from `gaetgodi_fol_jml2`):**
- `#__content` (`lqyfi_content`): 64 articles total, ~45 published (`state=1`)
- `#__menu` (`lqyfi_menu`): 132 rows, 13 top-level "mainmenu" items (Home, Lodges, Outposts, FAQ, Gallery, Weather [external link], Contact Us, plus a few unpublished/test items)
- `#__categories`: 31 content categories with nested paths (e.g. `accomodation/outposts/white-owl`)
- `#__redirect_links`: **empty** — Joomla's own redirect component was never populated, so there's no prior redirect history to mine.

**Sample test (28 representative URLs, both content-article and menu paths, built from the above data):** see §1.1 table. Full article/menu/category lists are available in my working notes if you want the complete 45-URL set rather than the sample — say the word and I'll produce the full table.

**Existing redirect mechanisms found:**
- `.htaccess`: stock WordPress rewrite block only, no custom redirects.
- No nginx-level redirects in the Plesk vhost config beyond standard `X-Forwarded-*` headers.
- **Rank Math Redirections module**: active, 17 rules already present (§1.2).
- Joomla's `#__redirect_links`: empty, nothing to inherit.

**What I could not determine:** the exact set of URLs Google actually has indexed from the old Joomla site (see §1.1's access note — GSC access needed). My reconstruction is derived from Joomla's routing logic, which should be correct for how Joomla generated these URLs, but I can't independently confirm every one was actually crawled/ranked without GSC or a Wayback Machine check (which I also didn't run — happy to, if useful, since Wayback is a public read-only lookup and doesn't touch your server).

### 2.2 robots.txt — clean
```
User-agent: *
Disallow: /wp-admin/
Allow: /wp-admin/admin-ajax.php

Sitemap: https://www.fishbucklake.com/sitemap_index.xml
```
Nothing blocking crawlers beyond the standard WP admin exclusion. No leftover Joomla `robots.txt` directives made it into the WP install (the old Joomla `robots.txt` in the quarantined tree was never carried over — good).

### 2.3 Indexability — clean
- `blog_public` option = `1` (site is **not** set to discourage search engines — a common post-migration accident, checked and ruled out).
- No `X-Robots-Tag` header on the homepage (checked via response headers).
- `<meta name="robots" content="follow, index, ...">` present and correct on the homepage via Rank Math.
- `siteurl`/`home` options both correctly set to `https://www.fishbucklake.com` — no leftover staging/IP references found in `wp_options` (checked `siteurl`, `home`) or in rendered canonical tags across the pages sampled.

### 2.4 Canonical URLs and hostname — correct
- Canonical tags on every page I checked are absolute, correct, and self-referential (e.g. `<link rel="canonical" href="https://www.fishbucklake.com/outposts/" />`).
- `http://fishbucklake.com` → `301` → `https://www.fishbucklake.com/` (confirmed via header trace). Both http-forcing and www-canonicalization are working correctly in one hop.
- No staging or bare-IP hostnames found in the canonical tags, `og:url`, or the `wp_options` siteurl/home values I checked.

### 2.5 Sitemap — exists, mechanically correct, but polluted (see §1.5)
Rank Math generates `sitemap_index.xml` → `post-sitemap.xml` (2 URLs), `page-sitemap.xml` (69 URLs), `category-sitemap.xml` (1 URL). All URLs use `https://www.fishbucklake.com` correctly. The mechanical setup is fine; the content in it is the problem (§1.5).

### 2.6 Compromise residue scan — mostly clean, two things worth noting
I scanned `post_content`, `postmeta`, and `options` for pharma/casino/replica spam keywords, `base64_decode`/`eval(` patterns, hidden `display:none` divs, and unexpected external link domains.
- **No spam injection found.** The one keyword hit (Terms of Use page, matched "pornographic") is legitimate boilerplate legal language, not injected spam. Verified by reading the surrounding text.
- **No base64/eval-obfuscated content found** in `post_content`.
- **Hidden-div hits are legitimate UI**, not injected: they're the Testimonials page's JS filter controls (`#testimonialFilters`, `#noResults`) which are meant to be hidden until a filter is applied. Verified by reading context.
- **External links in content** are limited to YouTube, MDN, WordPress.org/Foundation, and issuu.com — nothing anomalous.
- Where the real compromise residue actually lives is the quarantined Joomla tree (§1.4), not the live WordPress content — worth stating plainly since it's good news: whatever caused the compromise doesn't appear to have left spam in the WP content that got migrated over.

**What I could not determine:** postmeta was spot-checked via targeted queries (Rank Math meta, alt text, redirects) rather than exhaustively scanned key-by-key. If you want a full postmeta sweep for anomalous serialized payloads, that's a further pass I can do.

## (3) ON-PAGE — titles, headings, alt text, schema

### 3.1 SEO plugin — Rank Math, active
Rank Math (`seo-by-rank-math`, active) is the site's SEO plugin. Modules enabled: link-counter, analytics, seo-analysis, sitemap, rich-snippet, WooCommerce, BuddyPress, bbPress, ACF, web-stories, content-ai, instant-indexing, role-manager, AI-visibility, redirections. **The Local SEO module is not enabled** — relevant to §3.4 below. No conflicting second SEO plugin found (Yoast/AIOSEO/SEOPress all absent).

### 3.2 Title tags and meta descriptions
Of 71 published pages + 1 published post, **23 have a Rank Math title/description set**; the other **49 have neither** (`rank_math_title`/`rank_math_description` both `NULL`) — Rank Math falls back to its default title template (post title + site name) and no meta description at all for those. Of the 23 that do have custom SEO copy, it's genuinely well-written, unique, and geographically specific (e.g. "White Owl Lake Outpost | Remote Fly-In Fishing Ontario") — someone clearly did real SEO copywriting work on the core lodge/outpost/rates/hunting pages at some point. It just didn't reach the rest of the site.

Missing on real content pages worth fixing: `Information`, `Weather`, `Brochure`, `Videos`, `Buck` (slug `buck-3`), `Accomodation`, `Bayfield Lake Outpost`, `Boats & Motors`, `Ice Out Report`, `Maps`/`Map` (duplicate pages, see §4.1), `Catch and Release Policy` (the duplicate, see §4.1). The rest of the 49 with no meta are the demo/junk pages from §1.5, which don't need SEO copy — they need to not be published.

**Duplicate pages with different meta status:** `Privacy Policy` exists twice — `privacy-policy-2` (ID 3, has custom SEO meta) and `privacy-policy` (ID 4381, the slug you'd expect to be canonical, has none). Similarly `Catch and Release Policy` exists as both `catch-and-release-policy` (has meta) and `catch-and-release` (doesn't). Worth resolving which is canonical and redirecting/removing the other — this is a self-inflicted duplicate-content issue, unrelated to the Joomla migration.

**No generic/placeholder titles found** among post_title fields ("Home", "Page", "Untitled" etc. don't appear) — the raw WP post titles are all reasonably descriptive, even where Rank Math SEO title is unset.

### 3.3 H1 — see §1.6 (critical, listed there since it's sitewide)

### 3.4 Structured data (schema.org)
The homepage carries a Rank Math-generated JSON-LD graph with `@type: ["Campground","Organization"]`, `WebSite`, `WebPage`, `Person`, and `ImageObject` nodes. **No `address`, `telephone`, or `geo` properties appear anywhere in the schema** — I checked directly for those keys and found none. Rank Math's **Local SEO module is not active** (confirmed via the enabled-modules list in `rank_math_modules`), which is exactly the module that would let you set business type, address, phone, hours, and geo-coordinates and have them emitted as schema.

**Why it matters:** for a lodge business where search intent is inherently geographic ("fly-in fishing Northern Ontario," "outpost cabins near Hornepayne"), `LocalBusiness`/`LodgingBusiness` schema with a real `PostalAddress`, `telephone`, and `geo` is exactly the structured signal Google uses for map-pack and local-intent results. Right now there's schema, but it's the generic default, carrying none of the business's actual location data.
**Fix:** Enable Rank Math's Local SEO module and fill in business type (`LodgingBusiness` fits best), address, phone, and coordinates. Note the business has **two seasonal mailing addresses** (see §4.2) — decide which one (likely a P.O. Box won't geocode usefully for `geo`; you may want the physical camp location or Hornepayne as the service area instead) represents the business for schema/Google Business Profile purposes before filling this in.
**Effort:** Low (plugin module + settings form), but needs a decision on which address to use.

### 3.5 Image alt text
- Media library: **1,734 image attachments total**, **500 have non-empty alt text (29%)**, **1,234 have none (71%)**.
- `[fbl_gallery]` shortcode: **it does support alt text** — I read the shortcode source (`inc/gallery.php`) and confirmed it renders images via WordPress core's `wp_get_attachment_image()`, which automatically pulls the `_wp_attachment_image_alt` meta and emits it as the `alt` attribute. So this is **not a code gap** — whatever alt text is set on an image in the media library will appear correctly wherever `[fbl_gallery]` uses it. The 71% gap is a content problem (alt text was never filled in), not a shortcode limitation.
**Fix:** Bulk alt-text pass on the media library, prioritizing images actually used in `[fbl_gallery]` instances on the highest-traffic pages (outposts, lodges, gallery pages).
**Effort:** High in volume (1,234 images) but mechanically simple; could be batched by folder/category rather than done one-by-one.

**What I could not determine:** which specific images are missing alt text *and* are actually placed on which specific published page (I have the aggregate media-library number, not a per-page breakdown of gallery contents, since `[fbl_gallery]` pulls by FileBird folder at render time rather than storing IDs in post content). If useful, I can map FileBird folders to the pages that reference them and produce a per-page missing-alt count.

### 3.6 Image file sizes
2,958 image files in `wp-content/uploads` are over 300KB, totaling **~2.1GB**. The largest originals run 4–9MB each (e.g. `IMG_5728.jpg` at 9.05MB, `20230904_101559_53424876664_o.jpg` at 7.52MB) — these look like un-resized camera/phone originals uploaded directly. WordPress does generate smaller registered sizes automatically, but at this volume and with this little apparent compression discipline, it's worth confirming the theme/gallery is actually serving the appropriately-sized version rather than the full original in `<img>` tags (I did not verify this per-image; see §3.7's page-weight numbers, which are consistent with oversized assets being served).
**Fix:** Bulk re-compress/resize library (a tool like ShortPixel/Imagify, or a one-time CLI pass with `imagemagick`) and confirm the gallery/theme markup requests appropriately-sized image variants rather than `full`.
**Effort:** Medium — bulk tooling exists for this, but 2,958 files is a real batch job.

### 3.7 Page weight (homepage + one gallery page)
| Page | Requests | Total weight |
|---|---|---|
| Homepage (`/`) | 182 | ~20 MB |
| Gallery (`/catch-gallery/`) | 78 | ~9.9 MB |

Both are heavy by any modern standard (Google's own guidance targets well under 1–2MB and well under 50 requests for a fast-loading page). This is consistent with the oversized-image findings above and the very request-heavy Divi builder markup. Page speed is itself a Google ranking factor (Core Web Vitals), separate from the content/indexability issues elsewhere in this report.
**Fix:** Image optimization (§3.6) will likely have the single biggest effect; secondary wins available in Divi asset loading (script/style consolidation) but that's a performance audit in its own right, beyond this SEO scope.
**Effort:** Not scoped here — flagging as a known contributor, full page-speed audit would need its own pass (Lighthouse/PageSpeed Insights, which I didn't run since it queries a third-party Google service — say the word if you want that added).

## (4) CONTENT — thin pages, NAP, local signals

### 4.1 Thin / low-value content
Rendered word counts (visible text, including ~200 words of shared nav/footer chrome that appears on every page) range from ~205 words up to ~2,554. Because of that shared chrome baseline, **anything landing near 200–260 words has essentially no unique body copy** — that's the real "thin" list:

`Accomodation` (205), `Blog` (210, structural/empty), `Cottages` (212), `Offers` (212), `Services` (212), `Shop` (213), `Our Services` (216), `Brochure` (217), `Booking Canceled` (218), `Rooms – Compact/List View` (218), `Videos` (219), `Rooms – Background Media View` (220), `Rooms – Grid View` (222), `Transaction Failed` (231), `Slider and Carousel` (236), `Information` (239).

Most of this list overlaps with the demo-content pages already flagged for removal in §1.5 — once those are unpublished, the thin-content problem mostly resolves itself. The genuine exceptions worth actually writing content for: **`Accomodation`, `Brochure`, `Information`, `Videos`** — these are real navigational pages a visitor could land on that currently carry almost no indexable text of their own.

Duplicate/competing pages also dilute content signal: two `Privacy Policy` pages, two `Catch and Release Policy` pages, `Map` and `Maps` both live, `Buck` (`buck-3`) vs `Buck Cabins` as separate pages with overlapping topics.

**What I could not determine:** true unique-content word counts with template chrome subtracted programmatically — I estimated the ~200-word baseline by inspection rather than precisely isolating `<main>`/`<article>` content, since the Divi markup doesn't cleanly separate them in a way that's reliable to script. Directionally correct, not to-the-word precise.

### 4.2 NAP (name, address, phone) — as it literally appears on-site
Business name is used inconsistently across the site (exact strings, unnormalized, as instructed):
- "Fish Buck Lake" (short form, used in `MetaAuthor`/branding contexts historically and still in some titles)
- "Fish Buck Lake Wilderness Lodges and Outposts" (most common, used in most Rank Math titles/descriptions)
- "Buck Lake Wilderness Lodges and Outposts" (used in the JSON-LD `Organization.name`, `og:site_name`, and on the Contact page's address block itself — **note this drops "Fish" entirely**, unlike the other two forms)

Two mailing addresses appear on the Contact page (`/contact-us/`), labeled Summer/Winter, exact strings as rendered:
```

P.O. Box 577
Hornepayne, ON

Winter:
Buck Lake Wilderness Lodges and Outposts
```

Same phone number for both, different mailing addresses. This is legitimate for a seasonal fly-in lodge business (correspondence address changes by season), but:
- **Neither address appears in the site's schema.org markup at all** (§3.4) — Google currently has zero structured address data to work with.
- The site name used in this address block ("Buck Lake Wilderness Lodges and Outposts") doesn't match the name used in page titles ("Fish Buck Lake Wilderness Lodges and Outposts") — a small but real NAP-consistency gap that matters for local SEO / Google Business Profile matching.
- Two-address businesses need a documented decision for schema/GBP purposes (which address is "the" listed one, or whether both should appear as `ContactPoint`/service-area data) — this is a business decision I can't make for you, flagging it rather than guessing.

### 4.3 Geographic signal in text
The **only page that plainly states the region/nearest town in body text is `/location/`**: "Fish Buck Lake is a 15–30 minute floatplane flight from Hornepayne, Northern Ontario," with driving/VIA Rail directions. The homepage itself, despite having "Northern Ontario" in its meta description and title, does **not** mention "Hornepayne" in its visible body text at all (checked directly — zero matches), and "Ontario" only appears in template chrome/nav, not as a clear locational statement in the hero content.

**Why it matters:** a crawler landing on the homepage — the page most likely to be the primary indexed entry point — currently has to infer location from the meta description alone rather than from clear on-page text. For a geographic-intent business this is a missed, easy win.
**Fix:** Add a clear, plain-language locational statement to the homepage body copy (nearest town, province, access method) — not a keyword-stuffing exercise, just stating the fact that's currently confined to one buried page. (Per the brief, I'm not proposing specific copy or keyword targets — just flagging that the fact is present on the site but not on the page where it's most needed.)
**Effort:** Low.
